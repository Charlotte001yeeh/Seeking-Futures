## 0. 本规格要解决的问题

`04-总设计.md` 的展示层（§8）是按**日频**设计的：每日同步、SQLite 落库、前端只读。但 D1 的实际使用场景是**盯盘**——用户要的是"现在这一刻，20 日涨跌幅排前 20 的是谁"。

于是产生两个新要求：

| # | 要求 | 本规格对应章节 |
| --- | --- | --- |
| **R1** | 后端在**数据源 API 轮询流量范围内**实时更新前端，并保证数据流的**流通性**与**可信度** | §2 后端 · §3 数据流与可信度 · §4 流量预算 |
| **R2** | 前端布局符合人机交互规范、舒适合理，并**预留**每个品种的日 K 线、硬逻辑等信息位 | §5 前端 · §6 预留面板契约 |

**不在本轮范围**：D4 分析层实现、日 K 线抓取入库、局域网部署脚本、鉴权。

## 1. 实测基线（本规格所有节拍/预算的数字来源）

在真实交易时段（2026-09-18 下午盘）用 `tools/probes/rt-cadence.mjs` 轮询新浪 `hq.sinajs.cn`，逐合约记录每次「值发生变化」的时刻。

### 1.1 节拍：源本身约 **500ms 一拍（≈2 Hz）**

| 轮询间隔 | 采样窗口 | 合约数 | 观察到变化 | 最小间隔 | **中位间隔** | 最大间隔 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 250 ms | 13:31–13:43（12 分钟） | 15 | 13,469 次 | 249 ms | **515 ms** | 25,135 ms |
| **50 ms** | 13:43–13:45（2 分钟） | 3 | 672 次 | 50 ms | **469 ms** | 2,235 ms |

**判据**：轮询从 250ms 压到 50ms（快 5 倍），中位间隔几乎不变（515ms → 469ms）。**瓶颈不在客户端**，源本身约 500ms 刷新一次，再快也拿不到新值。

补充：新浪自己的时间戳字段粒度为 **1 秒**（连续取样为 `134319 134320 134321 …`）。

> ⚠️ 同一轮 50ms 采样里出现过 50ms 的最小间隔，这是**同一拍内多字段（最新价/成交量/持仓量）在请求边界上的抖动**，不是持续 20Hz 数据流。不能据此把刷新节拍定到 50ms。

### 1.2 各交易所差异（250ms 那轮的中位间隔）

| 交易所 | 代表合约 | 中位间隔 | 最大空档 | 备注 |
| --- | --- | ---: | ---: | --- |
| SHFE | RB2701 / CU2610 / AU2610 | 514–517 ms | 2.6–4.6 s | 约 2 Hz |
| INE | SC2611 / EC2610 | 514 / 527 ms | 2.3 / 7.2 s | |
| CZCE | MA2610 / TA2701 | 515 ms | 2.3 / 2.5 s | |
| DCE | M2701 / PP2701 / I2701 | 514–517 ms | 2.6–3.6 s | |
| GFEX | LC2701 / SI2611 / PT2612 | 515 / **771** / 531 ms | 4.6 / 7.7 / **10.0 s** | 流动性越低越慢 |
| **CFFEX** | IF2609 / T2612 | **1551 / 784 ms** | **19.5 / 25.1 s** | **显著更慢**，必须区别对待 |

**结论**：商品 ≈ 2 Hz 可用；**金融期货（中金所）只能用 1.5–2 s 级节拍**，且空档可达 20 s 以上，前端必须显示"该品种行情时间"而不是假定全局同步。

### 1.3 接口能力

| 项 | 实测值 |
| --- | --- |
| 端点 | `https://hq.sinajs.cn/list=<sym1>,<sym2>,…` |
| 编码 | **GB18030**（必须显式解码） |

| 错误率 | 250ms 轮询 12 分钟 / 2,806 轮 = **0 错误** |

| 交易所 | 规则 | 例 |
| --- | --- | --- |
| SHFE / INE / DCE / GFEX / CFFEX | `nf_` + 官方代码 | `nf_RB2701`、`nf_SC2611`、`nf_IF2609` |

## 2. 后端规格

### 2.1 组件与职责

```
┌──────────────────────────────────────────────────────────────────┐
│  本地服务（Node，独立进程；局域网绑定 0.0.0.0:<port>）              │
│                                                                  │
│  ┌────────────┐   ┌──────────┐   ┌──────────┐   ┌────────────┐  │
│  │ Scheduler  │──▶│ Poller   │──▶│ Normalize│──▶│  Ranker    │  │
│  │ 节拍/窗口   │   │ 批量取价  │   │ 字段映射  │   │ 换分子重排 │  │
│  └────────────┘   └──────────┘   └──────────┘   └─────┬──────┘  │
│        ▲                                              │         │
│        │ 退避/降级                                     ▼         │
│  ┌─────┴──────┐   ┌──────────┐   ┌──────────┐   ┌────────────┐  │
│  │ SourceHealth│  │ Snapshot │   │Broadcast │   │  Store     │  │
│  │ 健康与闸门  │   │ 内存态    │   │ WS + SSE │   │ 节流落库    │  │
│  └────────────┘   └──────────┘   └──────────┘   └────────────┘  │
│                                                                  │
│  基准侧（慢路径，每日一次）：                                       │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ DailyJob：六所官方日报 → 主力判定 → 基准日结算价 → 基准表  │   │
│  └──────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

| 组件 | 职责 | 关键约束 |
| --- | --- | --- |
| **DailyJob** | 每日 09:00 抓六所官方日报，产出**基准表**（品种 → 主力合约 + 基准日 + 基准日结算价） | 一次 ≈95 s；产出后**盘中不再变**，变更必须发 `baseDateChange` 事件 |
| **Scheduler** | 决定"这一轮该不该发请求、发多快" | 只在交易窗口内轮询；支持自适应退避 |
| **Poller** | 批量取实时价 | **单轮 1 个 HTTP 请求**（见 §4.2）；连接复用 keep-alive |
| **Normalize** | 字段位映射（商品 44 段 / 金融 50 段）、单位、时间戳解析 | 未知字段位 → 拒绝该条，不猜 |
| **Ranker** | 分子换最新价 → 重算 20 日涨跌幅 → 稳定排序 → 取双榜 | **分母（基准日结算价）盘中绝不变** |
| **Snapshot** | 维护"当前完整榜单"内存态，带 `seq` | 读请求只读内存，不查库 |
| **Broadcast** | 推送增量到前端 | 单轮只推一次；背压见 §2.5 |
| **Store** | 节流落库供历史与对账 | 不是每轮都写（见 §2.4） |
| **SourceHealth** | 错误率统计、熔断、降级 | 触发降级必须让前端可见 |

### 2.2 轮询节拍策略（回答"在流量范围内"）

**核心判断：源 500ms 一拍 ⇒ 客户端节拍低于 1s 是纯浪费。** 因此：

| 状态 | 节拍 | 触发条件 |
| --- | --- | --- |
| **主节拍** | **1.5 s**（可配 1–5 s） | 交易窗口内，且最近 5 轮内至少一次有值变化 |
| **自适应退避** | **5 s** | 连续 **10 轮**（≈15 s）无任何合约值变化（冷门时段、夜盘尾部） |
| **恢复** | 立即回主节拍 | 一旦检测到变化 |
| **窗口外** | **不发请求** | 非交易时段只做 60 s 一次的日历检查 |

**为什么默认不是 2 s 而是 1.5 s**：1.5s 与源 500ms 节拍是 3:1 关系，能稳定覆盖每一拍而不产生系统性漏拍；2s 是 4:1，边界上会偶发"同一拍取到两次"。1.5s 的额外流量在 §4 预算内。

**交易窗口（本地时区）**

| 时段 | 区间 | 说明 |
| --- | --- | --- |
| 日盘上午 | 09:00–11:30 | 商品 + 金融（金融 09:30 起） |
| 日盘下午 | 13:30–15:15 | 商品至 15:00，国债至 15:15 |
| 夜盘 | 21:00–次日 02:30 | 有夜盘的品种；**交易日归属下一交易日** |
| 周末 | 周五夜盘延续至周六 02:30 | 周六 02:30 后完全停 |

### 2.3 熔断与降级链

```
主源  新浪 hq.sinajs.cn
  │ 连续 3 次失败 / 单轮成功率 < 80%
  ▼
备源  腾讯 qt.gtimg.cn 或 东财 push2（契约见 §8.3）
  │ 同样失败
  ▼
降级  只用官方日报（当日/上一交易日快照），前端进入"非实时"模式
```

- 退避序列：`3s → 10s → 30s → 60s`，成功后**逐步**回升而不是立即回主节拍。
- 熔断状态、当前数据源、最近成功时间**必须**通过 `sourceHealth` 推给前端（§3.4）。
- **绝不**用旧值冒充新值：降级时前端显示的必须是"日报口径 + 明确标记"。

### 2.4 落库节流

每 1.5 s 写一次 SQLite = 一天 2 万+行 × 85 合约 = 写放大严重且无价值。策略：

| 触发 | 动作 |
| --- | --- |
| 距上次落库 ≥ **10 s** 且榜单有变化 | 写一条**榜单级**快照（40 行，双榜） |
| 某品种 `pct_20d` 相对上次落库变化 ≥ **0.05 pct** | 该品种单独写一条 |
| 交易日收盘后（15:15 / 次日 02:45） | 写**定稿**快照，标记 `final` |
| 每日 09:00 官方日报到位后 | 用官方真值**回填**当日盘中序列的最后一根，并做**对账**（§3.5） |

落库表新增（对齐 `04 §4.2` 风格）：

```sql
-- 盘中榜单快照（节流）
intraday_rank20(ts, trade_date, base_date, direction, rank_no,
                variety_code, main_contract,
                pct_20d, pct_1d, price, base_settle,
                quote_time, source, seq,
                PRIMARY KEY(ts, direction, rank_no))

-- 盘中价序列（按品种，节流后）
intraday_price(ts, trade_date, variety_code, main_contract,
               price, quote_time, source, is_live BOOL,
               PRIMARY KEY(ts, variety_code))

-- 数据源健康
source_health(ts, source, state, ok_cnt, err_cnt, last_ok_at, latency_ms)
```

### 2.5 推送与背压

- 传输：**WebSocket**（主）；**SSE** 作为降级（仅单向推送，兼容性好）。
- 单轮只推**一次**完整榜单（40 行 ≈ 6 KB）；**不做 delta**——40 行的完整快照足够便宜，delta 会引入状态同步 bug，是负收益。
- 背压：若某连接发送缓冲积压 > 512 KB，**丢弃中间的榜单消息只保留最新**（榜单是全量语义，丢中间态无害）。
- 心跳：无变化时每 **15 s** 发一次 `heartbeat`（含 `serverTime`），前端据此判断连接存活并校时。
- 慢客户端不阻塞轮询：广播是 fire-and-forget。

## 3. 数据流：流通性与可信度

### 3.1 端到端链路与时延预算

```
新浪源 ──▶ Poller ──▶ Normalize ──▶ Ranker ──▶ Broadcast ──▶ 前端渲染
  ①          ②           ③            ④           ⑤           ⑥
```

| 段 | 预算 | 实测/说明 |
| --- | --- | --- |
| ① 源侧数据龄 | ≤ 500 ms | 源 2 Hz 刷新（§1.1） |
| ② 网络往返 | ≤ 500 ms | 实测单轮 150 ms（境内） |
| ③ 解析 | ≤ 5 ms | 纯字符串 |
| ④ 重算排名 | ≤ 5 ms | 85 个品种内存排序 |
| ⑤ 推送 | ≤ 20 ms | 局域网 |
| ⑥ 前端重绘 | ≤ 50 ms | 40 行 DOM |
| **合计（源时间戳 → 屏幕）** | **≤ 2 s（p95）** | 含 1.5 s 轮询等待 |

**验收**：连续 100 轮采样，`前端行情时间` 与 `源时间戳` 的差值 p95 ≤ 2 s、p99 ≤ 4 s。

### 3.2 每条数字的溯源（可信度的最小单位）

榜单上**任何**一个数值，前端点开都要能回答：

| 字段 | 回答的问题 |
| --- | --- |
| `source` | 这个数来自哪个源（`sina_live` / `shfe_daily` / `czce_daily` / …） |
| `quote_time` | 源给出的行情时间（HHMMSS，秒级） |
| `recv_time` | 本地收到的时间（ISO8601 带时区） |
| `is_live` | **是否真的取到了实时价**（false = 沿用日报值，前端必须显式标记） |
| `trade_date` / `base_date` | 交易日 / 基准日 |
| `base_settle` | 分母（基准日结算价）及其来源文件 |
| `base_source` | 基准价来自哪一个官方日报接口 |
| `rolled_over` | 20 日窗口内主力是否换月过 |
| `main_reason` | 主力判定依据（T−1 量最大 / 因新合约无基准价而回落） |

**铁律（继承 `04 §4.1` 并扩展）**：`source` / `quote_time` / `is_live` / `base_settle` / `base_source` 缺任一 → **该行不得进入前端榜单**（宁可少一行可见的空缺，也不给一个无法溯源的数字）。

#### 3.2.1 实现备注：金融段的 `quote_time`（2026-09-23 修复）

体检发现：**8 个中金所品种 `is_live=true` 却 `quote_time` 为空**，直接违反上面的铁律。

根因是源字段位假设错误。实测（`realtime-server/test/probe-cffex-time.mjs` 逐位打印原始报文）：

| 段型 | 段数 | 行情时间 | 源标注交易日 |
| --- | --- | --- | --- |
| 商品 | 44 | `[1]` = `HHMMSS`（如 `150431`） | `[17]` = `2026-09-23` |
| 金融 | 50 | `[37]` = **`HH:MM:SS`（带冒号！如 `15:15:00`）** | `[36]` = `2026-09-23` |

早期注释写的是"金融段无此字段" → 置空。修复后金融段时间取 `[37]` 并归一化为 `HHMMSS`，
`fmtQuoteTime()` 同时接受 `HHMMSS` 与 `HH:MM:SS`。修完实测（真实报文）：

```
IF2612/IM2612/IH2612/IC2612 → 15:00:00（股指 15:00 收盘）
T2612/TF2612/TS2612/TL2612  → 15:15:00（国债 15:15 收盘）
```

这同时是一次**交叉校验**：解析出来的收盘时刻与中金所实际收盘时间一致，
说明字段位判断正确。回归守卫：`verify.mjs` 的 `U6a–U6d`（两种段型的字段位）与
`V8c/V8d`（盘中每个换价行、含金融行，都必须有合法 `quote_time`）。

### 3.3 三条"不许静默"规则

| 场景 | 必须的表现 |
| --- | --- |
| 某合约**取不到实时价**（月均价 `F` 合约、临时停牌） | 该行显示**日报值** + 明确的"非实时"徽章；不允许悄悄混进实时榜 |
| 全源失败 / 降级 | 顶部**全局横幅**："当前为日报口径，最后更新 HH:MM:SS"；榜单整列淡化 |
| 行情时间落后本地 > **30 s** | 顶部**陈旧告警**："数据可能陈旧（行情时间 HH:MM:SS）" |

### 3.4 状态消息契约

后端必须主动推送健康与口径事件（前端不能靠猜）：

| 事件 | 何时 | 载荷 |
| --- | --- | --- |
| `hello` | 连接建立 | `serverTime` / `protocolVersion` / `tradeDate` / `baseDate` |
| `snapshot` | 每轮 | `seq` / `serverTime` / `quoteTime` / `rows[40]` / `liveCount` |
| `baseDateChange` | 官方日报到位导致基准日/主力变更 | `from` / `to` / `reason` / `affected[]` |
| `sourceHealth` | 状态变化 | `source` / `state(ok\|degraded\|down)` / `errRate` / `lastOkAt` |
| `heartbeat` | 每 15 s | `serverTime` / `seq` |

### 3.5 可信度闭环：收盘对账

这是"确保数据可信"最重要的一环，且**只有后端能做**：

1. 盘中最后一次快照（15:15 或次日 02:45）落入 `intraday_rank20`，标 `final_intraday`。
2. 当日官方日报到位后（`DailyJob`），产出**官方定稿榜**。
3. 自动比对两者：
   - 成员重合度（目标 ≥ 19/20）
   - 各品种 `pct_20d` 偏差（预警阈值 **0.05 pct**）
   - 差异归因（主力是否换月 / 基准日是否前移 / 数据源差异）
4. 结果写入对账报告，**前端"数据健康"入口可见**；偏差超阈值时在首页打黄条。

> 逻辑上这与 `04 §6` 的校准闭环同源，只是从"日频对账"扩展为"**盘中 vs 定稿**对账"。

## 4. 流量预算（回答"在数据源 API 轮询流量范围内"）

### 4.1 只轮询榜内合约

| 方案 | 每轮合约数 | 相对流量 |
| --- | ---: | ---: |
| 全市场（六所全部合约） | ≈ 660 | 7.8× |
| **榜内品种主力合约（本方案）** | **85** | **1×** |

榜内合约已经覆盖了全部需要展示的对象；不需要的合约一个字节都不取。

### 4.2 单轮只发一个请求

新浪 `list=` 支持批量。85 个代码 ≈ 85 × 12 ≈ 1,020 字符，加到 URL 上约 **1.1 KB**，远低于常规上限。

**规格要求**：分片阈值设为 **120**（而非当前的 60），使 85 个合约**单轮 1 个请求**。

### 4.3 日流量估算

交易窗口合计 ≈ **585 分钟/交易日**（日盘 255 + 夜盘 330）。

| 节拍 | 轮次/日 | 请求/日 | 响应量/日（≈16 KB/轮） |
| --- | ---: | ---: | ---: |
| 1.0 s | 35,100 | 35,100 | ≈ 560 MB |
| **1.5 s（默认）** | **23,400** | **23,400** | **≈ 375 MB** |
| 2.0 s | 17,550 | 17,550 | ≈ 280 MB |
| 5.0 s（退避态） | 7,020 | 7,020 | ≈ 112 MB |

**合规闸门（硬约束，写进配置）**：

| 闸门 | 阈值 | 触发动作 |
| --- | --- | --- |
| 瞬时请求速率 | **≤ 1 req/s** | 超过则强制拉长节拍 |
| 每分钟请求数 | **≤ 60** | 同上 |
| 单日请求总数 | **≤ 40,000** | 达到后降至 5 s 节拍并告警 |
| 连续错误 | 3 次 | 进入退避序列（§2.3） |
| 单轮响应时延 | > 3 s | 记 `latency_ms` 告警，连续 5 次降级 |

> 实测水位供参考：50 ms 采样轮以 **≈18 req/s 持续 2 分钟（2,132 次请求）零错误**；250 ms 采样轮以 **≈4 req/s 持续 12 分钟（2,806 次请求）零错误**。说明 1 req/s 有很大安全余量；但**不能**把"短时没被限流"当作"可以长跑"，因此上述闸门按远低于实测无错水位设定。

### 4.4 其他省流量措施

- **HTTP keep-alive 复用连接**，避免每轮重做 TLS 握手。
- 请求头精简（不带 Cookie、不带多余 Accept）。
- 交易窗口外**零请求**。
- 关闭日盘后对已收盘品种的轮询（夜盘只轮有夜盘的品种）——可再省约 **30%**。

| 条款 | 规定 | 理由 |
| --- | --- | --- |
| **稳定排序** | 行以 `品种代码` 为 key 复用 DOM，**位置变化用 FLIP 动画（250 ms）**平滑移动 | 2 s 一次的瞬间跳行会让用户跟丢目标 |

### 13.1 位置与交互

- 位置：`<main class="boards">` **之后**、页脚之前（`web/index.html` 的 `<section class="ops" id="ops">`）。

### 13.2 数据源卡片（真探测，不是状态灯）

`GET /api/sources` → `{ at, elapsedMs, tradeDate, cached, okCount, total, sources[], local[], model }`
`POST /api/sources/probe` → 同上，但**强制**重新探测（`cached:false`）。

| 列 | 内容 |
| --- | --- |
| 源 | 新浪实时行情 / SHFE / INE / CZCE / GFEX / CFFEX / DCE |
| 地址 | **真实请求端点**（模板变量 `{d}/{y}/{ym}/{dd}` 已代入交易日） |
| 状态 | 绿点=正常 / 红点=异常（`ok` 布尔，非猜测） |
| 延迟 | 实测毫秒数 + 相对条形；<300ms 绿 / <1000ms 黄 / 其余红 |
| 说明 | 正常时给"解析出 N 个合约"这类**可核对**的结果；异常时给原始错误 |

关键实现约定：
1. **"连通"= 真的取到并解析出行数**，不是只 ping 通 URL。六所复用 `rank20-daemon/dist/exchanges.js`
   里**与日报采集完全相同**的抓取器与解析器（`EXCHANGE_FETCHERS` / `EXCHANGE_ENDPOINTS` / `expandEndpoint`），
   所以状态面板显示的行数与日报实际用的行数是同一个数。
2. `GET` 缓存 **60s**（避免每次刷新页面都打 7 个源）；`POST` 绕过缓存。同一时刻只允许一个探测在跑（并发合并）。
3. `tradeDate` 取基准表的交易日；没有基准表时回退到"今天/最近工作日"（`defaultTradeDate()`，不再硬编码日期）。
4. `local[]` 三件本地产物（同一行呈现"数据流通性"）：`base.json`（交易日/基准日/品种数）、
   `kline/`（合约文件数）、`盘中实时.md`（seq / 换价比例）。
5. 采集模块缺失时**如实报告**（`未找到采集模块 rank20-daemon/dist/exchanges.js`），不假装正常。

### 13.3 模型 API 卡片（Key 的持有与隐藏）

安全约定（局域网内部自用、无登录态，因此把 Key 关在服务端）：

| 规则 | 落地 |
| --- | --- |
| Key 存储 | 只在服务端数据目录 `<varDir>/model.json`，`mode 0600`（POSIX 生效；Windows 由用户目录 ACL 管控） |
| 对外视图 | `publicConfig()` 只有 `baseUrl / model / hasKey / keyMasked / savedAt / storePath`，**没有 apiKey 字段** |
| 掩码 | `maskKey()`：只露头 3 尾 4，中间固定 8 个星号（不泄露真实长度） |
| 输入框 | `type="password"` + `autocomplete="new-password"`；**提交后立即清空**，绝不回填明文 |
| 留空语义 | 保存时 `apiKey` 留空 = **保持原 Key 不变**（前端不需要回填明文） |
| 测试 | 在**服务端**发起，前端拿不到 Key；允许用"尚未保存的 Key"直接测（先测后存） |
| 清除 | `DELETE /api/model/key` |

连通性测试（`testModel()`，OpenAI 兼容协议）：
1. 先 `POST {baseUrl}/chat/completions`，`max_tokens: 1`（最贴近真实用法的探活，20s 超时）；
2. 失败再退 `GET {baseUrl}/models`（多数兼容服务都支持，15s 超时）；
3. 返回 `{ok, via, url, status, latencyMs, elapsedMs, model, reply|models, note}`，
   全失败时返回 `{ok:false, error, hint, attempts[]}` —— `attempts` 列出每次尝试的
   URL / HTTP 状态 / 响应体前 300 字符，**失败原因不吞**。

前端渲染：成功显示 `✓ 连通成功 · via · HTTP status · latencyMs`（有回包则显示模型回包前 60 字）；
失败显示 `✗ 连通失败 · error · hint`，`attempts` 以 `<pre>` 展开。

## 14. 双榜一屏展示（涨/跌榜零滚动条，2026-09-23）

需求原文（用户）：
> 修改前端显示布局，要求涨幅榜和跌幅榜作为主要展示界面，去掉这两个榜的滚动条，全部显示一眼可见。

### 14.1 布局结论

页面仍是**固定视口**（`body { overflow: hidden }`），但两块榜单**不再各自内部滚动**：

| 部位 | 改法 |
| --- | --- |
| `.tableWrap` | `overflow: auto` → **`overflow: visible`**（关键：榜内不再出现滚动条） |
| `thead th` | 去掉 `position: sticky`（没有内部滚动后无意义），高度固定 **26px** |
| `.board h2` | 高度固定 **30px**，字号 14 → 13.5 |
| 数据行 | 高度 = **`--rowH`**（由视口反推），`padding` 6px → 0、`line-height: 1.15`、`td.pct` 15 → 14px |
| 运行状态模块 | **默认折叠**成一行（只留标题条 + 摘要 + 展开按钮） |
| 状态横幅 | 高度固定 **32px**（并计入预算，避免它出现时挤掉第 20 行） |

### 14.2 行高预算（可算、可测）

```css
--chromeH: 260px;                                        /* 除 20 行数据以外的全部竖直占用 */
--rowH: clamp(18px, calc((100vh - var(--chromeH)) / 20), 42px);
```

`--chromeH` 的每一项都有显式高度，加起来 **239px**，取 260 留 21px 余量：

```
顶栏 56 + 横幅 32 + 运行状态折叠条 45 + 页脚 28
+ 榜单标题 30 + 表头 26 + 榜单容器上下内边距 20 + 榜单边框 2 = 239
```

由此得到的实测可行性（**含"浏览器逐行向上取整"的最坏情况**）：

| 视口高 | 行高 | 20 行 + chrome | 结论 |
| --- | --- | --- | --- |
| 1080 | 41px | 1079 | ✓ |
| 950 | 34.5px | 939 | ✓ |
| 900 | 32px | 899 | ✓ |
| 800 | 27px | 799 | ✓ |
| 700 | 22px | 699 | ✓ |
| 640 | 19px | 639 | ✓ |
| 620 | 18px（触下限） | 619 | ✓ |

**< 620px** 才退化为整页滚动（`@media (max-height: 620px)` 放开 `body` 滚动）——
注意：**任何时候都不给榜单加内部滚动条**，要么一屏看全，要么整页滚。

### 14.3 滚动策略：展开详情时放开**页面**滚动

行内展开的详情面板实测高度 320–560px（`fitPanelHeight` 按四板块最大内容量设定），
一屏放不下是正常的。因此：

- 默认：`body { overflow: hidden }` —— 双榜一屏看全、零滚动条；
- 展开某一行 / 展开运行状态：`app.js` 给 `body` 加 `.expanded` / `.ops-open`
  → `body { overflow-y: auto }` + `.boards { flex: 0 0 auto }`
  → **整页可滚**，榜单本身依旧不出现内部滚动条，详情完整可达；
- 收起后自动移除 class，回到"一屏看全"。
